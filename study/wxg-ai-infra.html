六道口述题

Q01 · 长 prompt 混入后，短请求也卡了，怎么排查？

模拟题，关联腾讯 AI Infra 实习一面的 Chunked Prefill。

60–90 秒首答。 我先按输入长度、输出长度和是否命中前缀缓存分组，对比变更前后短请求的 P95 首 token 延迟（TTFT）和相邻 token 间隔（Inter-Token Latency, ITL）。把 TTFT 拆成排队和进入引擎后的处理时间，同时看每轮 prefill/decode token 数、KV 使用率与抢占次数。如果排队上涨但 ITL 平稳，先看请求到达率、并发和准入。如果伴随抢占和重算，先查 KV 容量。如果短请求的 ITL 尖峰反复撞上长 prefill 的调度轮次，我会怀疑 prefill 和 decode 混批干扰。为了验证这个判断，我会回放同一份长短混合流量，只调整 prefill 分块或每轮 token 预算，看长迭代是否缩短、短请求的 ITL 尖峰是否减少，同时检查长请求 TTFT 和达标吞吐。单池调度仍达不到目标时，再评估 P/D 分离和 KV 传输开销。

先沿一条短请求看时间线

以下数字只用于理解指标。假设客户端在 0 ms 发请求，引擎在 10 ms 入队，调度器在 50 ms 首次把它排进批次。客户端在 90 ms 收到第一个 token，随后在 110 ms 和 180 ms 收到第二、第三个 token。

在哪里等 怎样从时间线上看出来
首 token 到达前 客户端 TTFT 是 90 ms，其中引擎排队占 40 ms（10 → 50）。其余时间还包括入队前的网络和网关、排上后处理输入、生成首 token 和回传。仅凭这组时间戳无法算出纯 GPU prefill 耗时。
已经在生成 两次 ITL 分别是 20 ms 和 70 ms。第二次间隔突然变长，重点检查 110 → 180 ms 之间发生了什么。用引擎和客户端的时间戳区分是引擎迟迟没产出，还是已经产出但网关尚未交付。

三种情况怎么区分

每轮 prefill token 数反映调度器安排了多少输入 token 进来计算，decode token 数反映本轮安排了多少生成工作。长请求的 prefill 和短请求的 decode 可以被安排进同一轮。若这一轮特别慢，已在生成的短请求就可能多等几十毫秒。活跃序列还需要 KV Cache 容纳历史 token。如果块不够，引擎可能让部分请求让出缓存，恢复时再重算部分状态，具体取决于抢占策略。

现象 优先验证
等待队列增长，ITL 平稳 看输入请求是否持续比完成请求多，以及运行请求数是否卡在准入上限。以时间线为例，若本来在 50 ms 排上，现在要到 100 ms，但后续输出节奏相同，先查首 token 之前的排队。
长 prefill 与高 ITL 时间对齐 把短请求的慢间隔与引擎的调度轮次对齐。如果尖峰反复落在 prefill token 较多的长迭代，再做一次只改变调度预算的对照，观察慢间隔是否减少。
KV 占用接近上限，抢占和重算上升 把 KV 占用、受影响请求的抢占与恢复事件对齐。降低同时运行的 token 规模再复测，观察抢占是否减少，同时量化排队和拒绝率的变化。单看占用率高不足以确认故障。
客户端卡顿，引擎指标平稳 对齐网关和客户端的流式时间戳，检查缓冲、写阻塞与连接重置。

怀疑长 prefill 拖慢短请求，怎么验证？

回到前面的例子。短请求在 110 ms 收到第二个 token，却要等到 180 ms 才收到第三个。假设对齐引擎时间线后，发现这种慢间隔反复落在长 prefill 和短 decode 同批的迭代里。这给了我们一个待验证的解释：单轮塞进了太多 prefill 计算，把短请求下一次出 token 的时间也拉长了。 仅凭时间对齐，还分不清是不是当时流量更高，或 KV 抢占恰好也发生了。

这里的 A/B 是两轮对照压测。A 保持原配置，B 只改一项。比如已经启用分块时，调低每轮 token 预算，让长 prefill 每轮少处理一些 token。两轮用同一模型和 GPU，按同一到达时间表回放相同的长短请求，用相同方式冷启动或预热缓存，并核对实际命中率。

先看原来偏慢的迭代是否缩短、短请求的 P95 ITL 是否随之改善。两个信号一起变化，就更支持混批干扰的判断。如果迭代缩短了但 ITL 尖峰仍在，回到时间线核对 KV 抢占或网关交付。最后看 长请求 P95 TTFT、达标吞吐和拒绝率。分块后短请求更流畅，也可能让长请求多等几轮。两类请求都满足延迟目标，再结合吞吐和拒绝率决定是否采用。若单池反复出现两类请求互相挤压，再测 P/D 分离。

追问 1 · Chunked Prefill 切的是什么？越小越好吗？

① 切什么？ 把同一条长 prompt 里尚未处理的输入 token按顺序分段，分几轮做 prefill。已有请求的 decode 可以和这些分段同批执行，普通自回归解码每个请求每步生成一个 token。

② KV 怎么用？ 每段算出的 K、V 都留在这条请求的 KV Cache 中。后续段做注意力时会读取前面各段的 KV，最后一段算完才生成这条长请求的首个输出 token。Prefill chunk 管每轮算哪些输入 token，PagedAttention 的 KV block 管算出的 KV 怎么存。 Sarathi 原论文 · vLLM KV 分页说明

③ 块大小怎么定？ 在 vLLM V1 的 chunked prefill 调度里，先安排待处理的 decode，再用 max_num_batched_tokens 的剩余预算安排 prefill。下面假设长请求未命中前缀缓存，每轮剩余预算都给它，因此前两轮各处理 512 − 128 = 384 个输入 token，第三轮处理剩下的 132 个。实际分段长度随负载变化。 vLLM V1 调优文档

调参记法。 把预算调小，一轮里能塞进的 prefill 工作更少，短请求的 ITL 可能改善。但长 prompt 可能要多跑几轮、反复读取前面的 KV，首 token 可能更晚。同一负载下扫几档预算，同时看短请求 P95 ITL、长请求 P95 TTFT 和达标吞吐。 Sarathi-Serve，OSDI 2024

追问 2 · 怎么算压测成功？

参考答案。 我会先定义延迟目标，例如每个请求的 TTFT 不超过 250 ms，TPOT 不超过 40 ms。TPOT 是首 token 之后平均每个输出 token 的耗时。如果用户特别在意偶发卡顿，我还会单独看 ITL 的尾部。假设稳态统计 60 秒，有 680 个请求成功完成，其中 600 个同时满足两项要求，那么达标吞吐是 10 请求/秒。对比 A/B 时我会带上实际到达率、长短请求各自的达标率、错误率和拒绝率。有额外 GPU 时，也比较每卡达标吞吐或每个达标请求的成本。vLLM 压测指标

追问 3 · P/D 分离后，怎么定位首 token 慢？

参考答案。 我会用同一个请求 ID 串起网关、Prefill（P）和 Decode（D）的 trace，先看这个实现在哪里生成首 token、什么时候把它交给客户端。再记录 P 入队与开算、P 算完、首 token 生成与交付、KV 可读，以及 D 开始生成的时间。如果是 P 排队拉长，查 P 池负载。如果已经生成首 token 但客户端迟迟收不到，查交付链路。如果实现要求 D 收到 KV 后才交付首 token，再把传输与 D 排队纳入 TTFT 的关键路径。

网关在这条链路里做什么？ 这里指推理服务面向调用方的入口。它接收应用后端的请求，转给推理系统，再把生成结果流式传回调用方。它也可以负责鉴权和限流。P 和 D 执行模型计算，选哪台 P、哪台 D 可以由独立的调度组件负责。

沿同一个请求 ID 排查。 假设网关给一次调用分配了 req-42，并把它传给内部服务。排查时用这个 ID 找到网关、P 和 D 对同一次请求的记录。假设这个实现从 P 端交付首 token，下面的时间是教学示例。

同一次请求的记录 从网关收到请求起
网关收到请求 req-42 0 ms
网关收到 P 发来的首 token 80 ms
网关把首 token 写入给调用方的响应流 120 ms

网关自己记录的两条时间戳相差 40 ms。这段时间已经花在网关收到 token 之后，先查响应缓冲或写阻塞。如果网关是到 120 ms 才收到首 token，收到后马上写出，就沿 req-42 查 P 的入队、开算与首 token 生成记录。若部署要求经 D 才交付首 token，再把 KV 就绪和 D 排队的记录接到同一条 trace 上。调用方何时真正收到 token，需要看调用方自己的记录。

怎么区分 KV 慢和 D 慢？ 假设首 token 在 P 端已经交付，但第二个 token 来得很晚。KV 迟迟未就绪，先查传输排队和有效带宽。KV 已可读却迟迟未被 D 调度，则先查 D 池的队列和容量。这两种情况都可能体现为首个 ITL 偏高。Serving 专题，第 4 章 · DistServe

Q02 · 权重装得下，服务为什么仍会 OOM？

模拟题。

60–90 秒首答。 显存还要容纳 KV Cache、运行时临时张量和工作区。先分清模型启动时失败，还是运行中出现 CUDA OOM、KV 分配不足或抢占。对标准全注意力的 GQA，我按每 token 的 KV 开销乘活跃 token 总数估算，再加上分块取整和预留。比如 32 层、8 个 KV 头、头维度 128、BF16 时，每 token 是 128 KiB，一条 8K 序列约 1 GiB，按未分片且不共享前缀计算。上线时用实际 KV 容量和输入、输出长度分布设置准入预算，按 token 容量看并发。长短请求混合时，可以限制最大上下文、对长请求做分流，再用抢占率、拒绝率和 P95 指标验证。

白板估算。 每 token KV 字节数 = 2 × 层数 × KV 头数 × 头维度 × 元素字节数。剩余显存扣除权重、工作区和安全余量后，再用实际每卡布局和缓存块大小算能容纳的 token 数。

追问

  • TP=4 会让每卡 KV 恰好变成四分之一吗？核对实际 KV 头的分片与复制。KV 头数小于 TP 规模时，部分实现会复制头。
  • PagedAttention 与 Prefix Caching 各改善什么？前者用分块管理 KV，减少连续预分配和碎片。后者复用共同前缀，省去匹配部分的 prefill 计算，并可共享缓存块。

Q03 · 部分节点有 RDMA，如何设计多卡推理？

据腾讯 AI Infra 实习一面和腾讯混元推理一面改写。

模型如何放进节点，服务如何扩容

先确定一个副本需要多少卡。 一个推理副本能独立完成一次模型推理。它可以跑在一张卡上，也可以由多张卡用 TP 或 PP 共同承担。估算一个副本的资源时，要给模型权重、目标并发和上下文长度对应的 KV Cache，以及运行时工作区留出显存。放得下一个副本之后，就可以复制整套部署，让不同副本处理不同请求。这就是稠密模型服务里的推理 DP。每个副本通常各自维护 KV Cache，路由时可以同时看排队长度和前缀命中的机会。

再把模型切分和机器拓扑对上。 TP 把同一层的矩阵切到多张卡。在经典稠密 Transformer 中，每层 Attention 和 MLP 的输出都要在 TP 组内各做一次 All-Reduce。把组内的卡放在同一节点的高速互联域，通常能降低这类高频通信的成本。PP 让每个阶段负责连续几层，计算到阶段末尾才把中间激活交给下一阶段。因此，一个副本必须用多台机器时，可以考虑让节点内的卡组成 TP 组，再用有 RDMA 的节点间链路连接 PP 阶段。PP 会引入跨机传输和阶段等待，跨节点 TP 也可以纳入实测对比。vLLM 并行与扩展

60–90 秒首答

我会先问清一份模型加目标 KV Cache 要多少显存，哪些 GPU 在同一个 NVLink 域，哪些节点之间有 RDMA，以及延迟目标是什么。如果单节点能放下，我会先选节点内的 TP 配置。吞吐不够时，用同一负载对比扩大 TP 和增加副本，后者可以通过排队和前缀缓存命中来路由。如果单节点放不下，我会先在打通 RDMA 的节点间试 PP，尽量把每层的集合通信留在节点内，并测阶段是否均衡、流水线空闲多少。MoE 还要看专家放置、跨节点 All-to-All 和热点专家。最后用代表性负载比较达标吞吐、P95 TTFT、P95 ITL 和每卡成本，再用 NCCL 和 GPU 时间线确认瓶颈。

算例 · 两台机器，各 8 张卡

  • 单机放得下，主要想接更多请求。 假设模型与目标 KV 容量正好要 8 张卡。两台机器各跑一个 TP=8 的副本，即 DP=2。请求 A 可以在第一台机器完成，请求 B 可以同时在第二台完成。
  • 单机放不下，需要两台合起来跑。 假设模型按层分成两段后，每段连同自己负责的 KV 都能放进 8 张卡。两台各跑一个 TP=8 的阶段，再连成 PP=2，共同组成一个副本。请求 A 先在第一台经过前半层，再从阶段边界把激活送到第二台计算后半层。

白板推导。 写成 Y = XW。第一层按输出维切列，每张卡拿到自己的中间特征片。逐元素激活直接在本地做。第二层按输入维切行，每张卡用对应中间特征计算对完整输出的部分和，最后用 All-Reduce 得到每卡完整输出。如果下一步可以接分片输出，则可用 Reduce-Scatter 保留各卡对应的片。先说清每一步的输入和输出张量形状，再说通信。

追问 · 如何报出 TP、PP、DP、CP、EP 的通信量？

沿用「AI Infra 基础」里的口径。公式只计发出的有效载荷，单位是字节。代入前先看每一行的统计范围，再决定是否乘层数、microbatch 数或卡数。

符号说明

符号 含义
A 完整激活张量的大小，A = B × S × H × b 字节。
B、S B 是单个 microbatch 的样本数，S 是每条序列的长度。这里按同长度张量 [B, S, H] 估算。
H、b H 是 hidden size，b 是每个激活元素占的字节数。BF16 和 FP16 都是 2 字节。
t、p t 是一个 TP 组里的卡数，p 是一条 PP 流水线的阶段数。
D、c、e D 是一个训练 DP 组里的 rank 数，c 是一个 CP 组里的卡数，e 是一个 EP 组里的卡数。EP 卡数和专家总数是两个量。
N_local、b_g N_local 是本 rank 上参与这次 DP 梯度同步的参数元素数，b_g 是通信时每个梯度元素占的字节数。两者相乘得到梯度缓冲区大小。
H_kv 单份 K 或 V 的宽度，等于 KV 头数 × 每头维度。公式里的系数 2 同时计入 K 和 V。
T_local、k T_local 是当前 rank 进入 MoE 路由器的实际 token 数，k 是每个 token 选择的专家数（top-k）。两者相乘得到 token 到专家的分配次数。
并行方式与统计范围 前向发送量 训练发送量
TP，每卡、每 Transformer 层、每 microbatch 4(t−1)A/t 8(t−1)A/t
PP，整条流水线、每 microbatch (p−1)A 2(p−1)A
DP/DDP，每卡、一次完整梯度同步 仅计梯度同步时为 0 2(D−1)N_local b_g/D
CP，每卡、每 Attention 层、每 microbatch 2(c−1)BSH_kv b/c ≈ 6(c−1)BSH_kv b/c
EP，每卡、每 MoE 层、每 microbatch ≈ 2(e−1)T_local kHb/e ≈ 4(e−1)T_local kHb/e

各式的条件。 TP 按经典稠密层、无 SP 和重计算、每层前向两次 Ring All-Reduce 估算。PP 按非交错、每阶段一张卡、无 TP/SP 的基线计算，训练式假设激活和激活梯度同精度。DP 一行只算训练 DDP 的梯度同步，按 Ring All-Reduce 估算。CP 按完整 KV 环形交换估算，训练式假设反向重取 KV。EP 按各卡均匀路由、无 padding 或丢弃的标准 All-to-All 估算。

TP 和 PP 算例。 对同一份 A = 64 MiB 激活，TP=8 时，每次 Ring All-Reduce 每卡发送 112 MiB，一层前向两次就是 224 MiB/卡。再看 PP。用原笔记的 A = 64 MiB，把 32 层分成 4 个阶段，一批前向只跨 3 个边界，共发 192 MiB。训练还要沿这 3 个边界传激活梯度，同精度时合计 384 MiB。这两项都是全流水线总发送量。普通单 token decode 每步改用 (p−1) × B_active × H × b，其中 B_active 是当步活跃序列数。传的是当前 token 的 hidden state，历史 KV 留在拥有对应层的阶段。

Q04 · DDP 和 FSDP 一轮训练各在哪里通信？

模拟题。

一次参数更新会用到哪些状态

这里把一次训练迭代理解为一次参数更新。前向用模型权重计算输出，反向根据训练损失计算梯度，优化器再根据梯度更新权重。Rank 是分布式进程的编号，这里的例子按一个 rank 管一张 GPU 来看。每个 rank 处理不同的小批数据，因此先算出各自的本地梯度。

  • DDP（Distributed Data Parallel，分布式数据并行）让每张卡保留完整模型副本。它把多个参数的梯度装进一个梯度桶，桶里的梯度就绪后一起通信，让同步尽早和剩余的反向计算重叠。
  • **FSDP（Fully Sharded Data Parallel，全分片数据并行）**把参数、梯度和优化器状态分片存放。优化器状态是更新参数用到的历史数据，例如 Adam 的一阶和二阶矩。全分片时，每张卡平时只常驻自己负责的分片。
  • 三个集合通信操作。 All-Reduce 对各卡的张量按位置归约，每张卡都获得完整结果。All-Gather 把各卡的不同分片拼成完整张量。Reduce-Scatter 先归约，再把结果切成分片交给各卡。训练里需要平均梯度时，再计入相应的缩放。

60–90 秒首答。 DDP 的每个 rank 保存完整参数和优化器状态，各自做不同数据的前后向，再对梯度桶做 All-Reduce，通常尽量与反向计算重叠。以 PyTorch FSDP 全分片为例，平时每个 rank 只留参数、梯度和优化器状态的分片。模块计算前 All-Gather 参数，配置为前向后重新分片时，反向前还需取回完整参数。反向得到梯度后 Reduce-Scatter，每卡只更新自己拥有的分片。节省的是常驻状态显存，模块临时聚合仍有峰值。调优时同时看分片粒度、预取、通信和计算重叠，以及激活与参数峰值。

两张卡走一轮。 两张卡处理不同的小批数据，参数从 [10, 20] 开始。本地反向得到的梯度分别是 [2, 4] 和 [6, 8]。用学习率 0.1 的普通 SGD，先同步梯度，再更新参数。

操作 Rank 0 Rank 1
DDP 同步后的梯度 [4, 6] [4, 6]
DDP 更新后的参数 [9.6, 19.4] [9.6, 19.4]
FSDP 同步后的梯度分片 [4] [6]
FSDP 更新后的参数分片 [9.6] [19.4]

DDP 的 All-Reduce 按对应位置归约。两张卡的梯度相加得到 [8, 12]，默认取平均后，每张卡都有完整的 [4, 6]。随后每张卡各自执行 optimizer.step()，用同样的梯度更新自己的完整参数副本。

FSDP 全分片的前后向顺序。 以一组模块参数为例，Rank 0 常驻 [10]，Rank 1 常驻 [20]，并开启前向后重新分片。

  1. 前向前 All-Gather。 两张卡都拼出完整的 [10, 20]，各自计算本地数据的前向。
  2. 前向后重新分片。 释放临时拼出的完整参数，各卡保留自己的参数分片。
  3. 反向前再次 All-Gather。 两张卡重新拼出前向时的参数，再为各自的数据做反向。比如两层按 A → B 做前向，反向就先为 B 取回参数并计算，再处理 A。
  4. 反向后 Reduce-Scatter。 每张卡先为本地数据算出覆盖整组参数的梯度。通信按位置归约，并把结果按参数所有权分发。计入平均缩放，Rank 0 得到第一位 (2+6)/2 = 4，Rank 1 得到第二位 (4+8)/2 = 6。每片都汇集了两卡的贡献。
  5. 各卡更新自己的分片。 Rank 0 把 [10] 更新为 [9.6]，Rank 1 把 [20] 更新为 [19.4]。下一轮 All-Gather 时，两卡都能拼出更新后的 [9.6, 19.4]。

为什么反向还要取回权重？ 以线性层 y = w × x 为例。设上游传回的梯度为 g，本层权重梯度是 g × x，而传给前一层的输入梯度是 g × w，所以反向还要用到前向时的权重。前向后释放完整权重可以节省显存，代价是反向前再通信一次。若配置为保留完整权重，就可以省掉这次 All-Gather。

追问 1 · FSDP 省了状态显存，为什么仍可能 OOM？

训练显存随时间变化。常驻显存在一次迭代的大部分时间里都占着，例如参数分片和优化器状态。激活是前向产生的中间张量，部分要保留给反向。临时工作区是算子计算时使用的额外缓冲。FSDP 在执行某组模块前，还要通过 All-Gather 在每张卡上拼出这组完整参数。预取是当前模块还在算时，就提前发起下一组参数的 All-Gather，以减少等通信的时间。两组参数可能在同一时刻占用显存。PyTorch FSDP2 预取说明

算例 · 一张 24 GiB 的卡。 以下数字是假设值，列的是同一时刻可能共存的显存。

这一刻占用的显存 大小
常驻的分片训练状态 3 GiB
仍需留给反向的激活 10 GiB
正在计算的模块拼出的完整参数 4 GiB
本轮算子的临时工作区 4 GiB
预取的下一组完整参数 4 GiB

前四项共 21 GiB。如果预取的参数在这时也已驻留，需求就到 25 GiB，超过卡的容量。即使平时只有 3 GiB 的分片训练状态，这一步仍可能触发 OOM（Out of Memory，显存不足）。

参考答案。 我会先找到出错发生在哪个阶段和哪张卡，沿显存时间线看当时哪些张量同时存在。如果在 All-Gather 或预取时显存冲高，先减少预取或缩小每次一起聚合的参数组，再看省下了多少峰值、吞吐掉了多少。如果主要是激活占用，就试着减小 microbatch，或者用激活重计算。激活重计算会少保留一部分前向中间结果，在反向需要时重新算。最后用相同模型和负载核对峰值显存与每步耗时。

追问 2 · 训练中途故障，怎么恢复？

**Checkpoint（检查点）**是某个训练时刻的可恢复快照。通常在一次参数更新结束后建立快照，让权重、优化器状态和已完成步数对应同一个边界。学习率调度器决定每一步使用的学习率，数据游标记录下次该读哪批数据，随机数状态让采样、数据增强或 dropout 从对应的随机序列继续。只拿模型权重继续跑，会丢掉优化器的历史状态，也可能从错误的数据位置或学习率重新开始。

快照里要保存什么 恢复时用来做什么
模型参数、优化器状态 用对应步的权重和动量等状态继续更新。
已完成的全局训练步、学习率调度器状态 恢复训练计数和下一步学习率。使用梯度缩放时，也保存缩放器状态。
采样器或 DataLoader 状态、数据游标、各 rank 的随机数状态 找到下一个待训练的数据批次，并恢复对应的随机状态。游标以训练实际消费的位置为准，不能用已提前读入队列的位置。

算例 · 只从完整检查点恢复。 假设每 10 步保存一次。第 1000 步的检查点已成功写完。第 1010 步启动异步写入，进程在写完前因故障退出。恢复时选择第 1000 步的完整快照，重建模型、优化器和数据读取状态，从第 1001 步重跑。异步保存时，启动写入只代表提交了保存任务，等所有分片和元数据写完、确认成功后，才把那一版标记为可恢复。

参考答案。 我会在统一的优化器步边界保存训练状态。FSDP 可以用 PyTorch Distributed Checkpoint 保存各 rank 的分片，并随检查点记录训练步、调度器、数据进度和随机数状态。故障后重建训练进程组，加载最近完整的一版。恢复后先核对三个数：已完成步数、下一批数据的位置、下一步学习率。如果数据读取或随机数状态无法精确还原，就把恢复说明写成从最近检查点重跑，并说明哪些部分无法完全复现。PyTorch 分布式 checkpoint · PyTorch 异步保存示例

Q05 · rollout 跟不上训练，怎么调度并控制样本滞后？

模拟题。

先看 rollout 怎样给训练提供数据

在大模型强化学习里，策略就是负责生成回答或动作的模型。Rollout 是用某一版策略对一批输入采样，得到回答。做 Agent 训练时，采样还可能包括工具调用和环境返回，合起来是一条轨迹。样本打分后交给训练进程，训练进程算梯度、更新策略，再把更新后的权重交给下一轮生成。

用一条链路记住它：生成样本 → 打分 → 训练更新 → 发布权重 → 用新策略继续生成。如果训练 GPU 大部分时间在等样本，沿链路分别看生成、工具等待和打分的耗时。比如大量轨迹在等工具返回时，先查工具等待和调度，多加生成卡可能解决不了等样本的问题。

生成和训练怎样用 GPU

共用 GPU，就是两边按阶段轮流用同一批物理卡。 以 8 张卡的同步部署为例，先把当前策略权重载入生成引擎，用这 8 张卡生成一批轨迹。生成阶段结束，调度器暂停生成。引擎可以进入休眠，释放 KV Cache，并按配置将推理权重转移到 CPU 或释放，以腾出显存。接着训练进程用这 8 张卡做前后向和优化器更新。训练结束，再把更新后的权重装进生成引擎，恢复生成。这样同一批卡能先后承担两种工作。代价是对方运行时自己要等，释放和重新分配显存、迁移权重也会占时间。verl 生成阶段切换 · vLLM Sleep Mode

希望生成和训练同时进行，就给两边各自的 GPU 池。 假设 4 张卡能满足各自的部署需求，可以让 4 张卡专门跑 rollout，另 4 张专门训练，两边用队列交接已打分的样本。生成池执行的是完整的模型推理，包含 prefill 和 decode。训练池执行前后向和参数更新。Q01 的 P/D 分离发生在推理内部，拆的是 prefill 和 decode。这里拆的是整个 rollout 与训练，生成池内部也可以再做 P/D 分离。两个池能独立扩容，训练侧更新的权重则需要传给生成侧，并等生成侧加载完成后启用。verl 独立异步模式

两边并行后，样本为什么会滞后

拆池后，训练可以一边消费已有样本一边更新权重。与此同时，生成侧可能仍在完成用旧策略启动的请求。即使新权重已经加载，旧策略生成的样本也可能还在排队。策略版本差就是训练消费样本时，当前策略和生成该样本的策略相差多少个版本。因此我会把生成时用的策略版本随样本保存下来，训练取样时才能判断它有多旧。

算例。 假设每次训练更新都编号。生成侧用 v12 开始一条长轨迹，等它打完分并被训练取出时，训练侧已经到 v15，版本差就是 3。如果所用算法允许的最大版本差是 2，这条轨迹就超出了当前训练的接收范围。具体阈值取决于算法和实测，例子里的 2 仅用来演示判断过程。

队列上限控制还在积压多少工作。 如果训练消费跟不上，样本持续堆积，在队列中等待越久，就越可能跨过更多次权重更新。队列接近上限时，训练侧或队列可以反馈给生成侧，让它减慢或暂停接新任务，这就是背压。队列上限能控制积压，单条长轨迹仍可能在生成阶段就已经变旧，所以版本差还要在取样时检查。反过来，如果队列经常为空、训练卡一直等样本，就回头找生成、工具或打分哪个环节供不上。

60–90 秒首答

我会先把 rollout 的生成、工具等待和打分分别计时，结合队列深度和训练 GPU 空闲判断卡在哪。如果共用 GPU，我会先量清楚轮流切换要花多久，包括释放 KV Cache 和同步新权重。如果训练经常在等待，而生成和训练各自能用一组卡跑起来，我会试两个独立的 GPU 池，让一边生成、一边训练。两边同时跑之后，训练可能更新得比样本到达更快，所以我会给样本标记生成时的策略版本，按算法要求检查最大版本差。若样本开始积压，就用有上限的队列限制新增 rollout。最后用达标样本数、GPU 空闲时间、权重同步耗时和训练质量比较两种部署。

追问 1 · 推送权重时，怎样让一条轨迹只用一个版本？

在途请求是已经开始生成、尚未结束的请求。固定版本是指请求启动时选定一版权重，后续生成都用这版。如果算法要求整条 Agent 轨迹使用同一策略，那么即使中间停下来调用工具，工具返回后的下一次模型调用也要沿用这一版。KV Cache 是模型用当时的权重算出的中间状态，因此也要按版本隔离。

算例 · 从 v12 切到 v13。 请求 A 已经在 v12 副本上生成。先把 v13 加载到另一个可用的 rollout 副本，等这个副本的所有 rank 都加载成功，再把新请求 B 路由到 v13。A 继续在 v12 上生成，直到所有绑定 v12 的请求结束，才回收旧副本和它的缓存。如果只有一组卡，就先停止接新请求，等在途请求结束，再原地加载 v13，清理旧版本的 KV Cache，全部 rank 就绪后重新开放生成。vLLM 权重切换与暂停模式 · vLLM 权重传输

参考答案。 我会在请求开始时固定策略版本，并把这个版本写到生成结果里。资源够时，新版本完整加载并通过就绪检查后只接新请求，旧请求留在旧副本跑完。资源有限时就先停接新任务、排空旧请求，再原地切换。上线后我会核对同一条轨迹的模型调用是否都用了同一版本，以及是否有新版本复用了旧版本的 KV。

追问 2 · Rollout worker 崩溃后，怎么恢复？

Worker 是从队列领取实际工作的进程，例如负责生成轨迹的进程。任务 ID 标识一次逻辑任务，同一个任务重试时沿用 ID。领取租约是在一段时间内把任务交给本次领取的 worker。worker 完成工作后向队列确认，称为 ACK。如果它崩溃、租约到期且没有 ACK，任务可以重新交给其他 worker。重新投递可能产生重复执行，所以每个阶段按任务 ID 检查是否已经完成，再决定要不要运行。这就是幂等处理。可重试队列示例 · SQS 可见性超时

算例 · 轨迹写完，worker 在 ACK 前崩溃。 Worker A 领取 rollout-42，用 v12 生成轨迹，把轨迹和版本写到持久存储，并记录“已生成”，但还没来得及 ACK。租约到期后，Worker B 拿到同一个 ID，看到完整轨迹已存在，就复用它，从尚未完成的评分阶段继续。评分结果也按任务 ID 只提交一份。如果崩溃发生在轨迹写完之前，就重试生成，并记录实际使用的权重版本。若只能用 v13，就按算法对新版本样本的规则重新采样和验收。

参考答案。 我会用可重试队列和稳定的任务 ID，先持久化本阶段的结果与状态，再 ACK。重投后从最后完成的阶段继续，评分和训练取样都按 ID 去重，恢复时校验轨迹是否完整、策略版本是否符合接收条件。如果训练进程也会崩溃，已消费样本的位置要和训练 checkpoint 一起恢复。这样可以从同一个训练步边界重放，避免因恢复到不同的步数而漏掉样本或把同一份样本再次纳入一个已保存的更新。
